# 同席三国杀：易用性改进计划

日期：2026-10-29。评估基线：`main` / `229993a`（v2.0.1）。

初始计划完成后，用户已授权实施全部项目，并明确新手教学可选。当前实现与验收记录见 [UX_IMPLEMENTATION.md](UX_IMPLEMENTATION.md)。以下保留规划依据。目标是让玩家一眼知道轮到谁、自己能做什么、操作会影响谁，以及结算发生了什么。

## 已确认的现状

- 当前工作目录原为空，已从指定 GitHub 仓库首次克隆。
- 已有六阶段、基础自动结算、点选中央玩家框、双目标编号、自动存档和房主纠正。
- 进入摸牌阶段会自动摸两张，不能再增加一套前端摸牌逻辑。浏览器演练确认手牌从 4 增至 6。
- 自动技能仅覆盖部分基础被动与转化。点击技能名主要是查看文本、填写说明和发送公告，复杂效果仍由玩家执行。
- 玩家框按四列网格排列，距离显示为小字；血量仅显示数字。没有拖拽指定目标和血量变化动画。
- 很多合法性检查发生在提交之后；目标按钮没有随所选牌展示合法性与原因。选牌时允许积累多张，而通常出牌只需一张。
- 桌面与 390×844 手机布局已查看。四人演练的手机页面中，记录位于手牌上方，手牌区约从页面第 1123px 开始，需要滚动往返。
- 当前语法检查通过，现有 39 项测试全部通过。本轮没有复跑两套 WebRTC 浏览器回归脚本，也没有进行异地联机验证。

相关入口：`dist/index.html`、`dist/ui/app.js` 的 `renderTargets` / `render` / `renderCards` / `renderPending` / `actions`，以及 `dist/backend/rules.js` 的 `useCard` / `ruleAction` / `advancePhase`。

## 核心交互方案

### 普通出牌

1. 点选或拖起手牌；显示当前意图、合法目标和不可指定的原因。
2. 单目标牌拖到合法玩家松手提交；点击模式仍是选牌、点玩家、确认。
3. 自用或无指定目标的牌通过明确的使用区或情境按钮提交，不要求选一个无关玩家。
4. 多目标牌进入分步选择，完成后确认；铁索同时提供单目标、双目标、重铸三条清楚的路径。
5. 提交后显示处理中并阻止重复提交。失败时保留仍有效的选择，展示原因；同步后重新计算合法性。

拖拽只生成与点击相同的操作意图，不直接移动真实牌、扣血或摸牌。无效放下、`pointercancel`、Esc 和断线都不能产生半次操作。手机拖拽要有阈值与替代操作，避免与滚动冲突。

### 技能

先建立按武将版本区分的能力清单。技能文案继续只从 `dist/data/` 读取；能力元数据记录实现范围、所需输入和支持状态，不复制另一份技能文本。

- 已自动处理的被动：显示生效状态及适用范围，避免再给一个会重复结算的发动入口。
- 已支持的转化：选择技能、选择合法材料、选择目标或响应，系统校验并执行。
- 复杂手动技能：先提供步骤化说明与现有工具入口；步骤完成状态由玩家明确确认，不把公告视为效果已经执行。
- 新增自动技能：逐项实现触发时机、成本、次数与效果；涉及额外回合、觉醒、标记和特殊牌区时另列范围。首轮不承诺 101 个武将全部自动化。

### 阶段

优先改按钮文案、阶段提示与摸牌反馈。自动跨过阶段必须先具备可靠的触发窗口、待处理标记和手动介入点；当前尚未建模的复杂技能可能在准备、摸牌、结束阶段发动，不能只判断“没有判定牌”就跳过。

首轮保留明确的阶段推进。可选快速推进放在后续，默认关闭；规则或技能无法确认时停下等待。

## 实施顺序

### 第一批：交互基础与可读性

先做 01、02、06、07、10、15、19：围桌结构、合法操作数据、阶段与技能状态、格子血量、手机布局。先统一状态与交互结构，后续拖拽、响应、动画复用这一基础。

验收：桌面和手机均清楚显示当前玩家、可用操作和本人手牌；距离解释正确；没有把手动技能标为已自动实现。

### 第二批：完整出牌与响应

做 03、04、05、09、11、13：拖拽、双目标、自用牌、弃牌助手、转化和统一响应。

验收：能连续完成“摸牌 → 出杀 → 对方出闪或放弃 → 继续出牌 → 弃牌 → 交接回合”；点击、触摸、键盘均有可用路径。

### 第三批：结算反馈与日常操作

做 08、16、17、18、20、21：摸牌和血量反馈、状态装备、理牌、联机向导和日志。第 12 项先实现手动技能向导；新增自动技能作为独立小批次推进。

验收：玩家能看懂每次操作的结果；联机等待、拒绝和重连都有清楚状态；不会补播旧事件或重复执行。

### 第四批：新手引导与可选提速

做 14、22，并根据前三批使用反馈确定逐项技能自动化顺序。首轮不引入强制计时或自动替玩家出牌。

## 技术落点和约束

- `dist/index.html`：桌面区域结构、手机操作区、响应区和联机向导的语义化骨架。
- `dist/ui/styles.css`：2–8 人座次布局、血量格、状态图形、拖拽视觉、触摸尺寸、390px 布局和减少动态效果。
- `dist/ui/app.js`：先将目标选择、手牌选择、当前意图和响应组织成明确的本地交互状态；渐进拆分成小模块，避免整屏重建打断拖拽、焦点和动画。
- `dist/backend/primitives.js` / `rules.js`：统一卡牌、距离、转化和动作合法性逻辑；避免前端复制一套规则判断。提示只能使用该席位有权获得的信息，最终仍由后端校验。
- `dist/backend/engine.js`：投影只包含该玩家可见信息；新增技能状态或事件字段显式列出。一次失败操作不能部分改变原状态。
- `dist/backend/worker.js` / `dist/sync/`：继续由房主串行提交、去重和广播；必要时提供脱敏的事件标识用于动画，不能根据日志文本猜测或从其他玩家隐藏手牌生成提示。
- 如新增不兼容字段，显式处理 schema / 协议版本、旧存档迁移和双方版本提示；纯布局变化不无故更换协议。
- 保持无强制云后端、账号、收费 API 和运行时第三方依赖；不恢复侧栏目标下拉框。使用原生排版与 SVG，不引入未授权插画或音效。

动画必须使用稳定事件标识或单调游标，考虑一条命令触发多次伤害的情况。首次加载、恢复及重连只建立基线；仅比较前后血量不足以准确表达伤害来源，也不能把无变化的完整快照当作新事件。

## 验收与回归

1. 每个代码批次运行 `node scripts/check.mjs`、`node --test`；规则、牌区、权限、同步变更补有意义的失败场景测试。
2. 改规则或联机时运行现有 `browser-smoke.mjs`、`browser-rules.mjs`；修改断言以适应新呈现，同时保留现有隐私与规则验证意图。
3. 交互验证：杀的合法与超距目标、铁索单/双目标及重铸、借刀双目标视角、自用桃和酒、装备替换、无懈与反无懈、转化响应、弃牌和濒死救援。
4. 拖拽验证：拖错位置、取消、触摸中断、拖动期间远端状态变化、连续点击、等待确认、旧版本拒绝、阵亡目标；均不得丢牌、重复出牌或误扣血。
5. 布局查看 1440px 桌面、390px 手机和 2/4/8 人局；验证长昵称、大量手牌、装备与判定牌同时存在、对话框及横竖屏。
6. 键盘、焦点、读屏描述、非颜色提示和减少动态效果可用；每条拖拽路径都有点击替代。
7. 重连与隐私：响应中刷新、拼点未公开时恢复、原席位重连；普通玩家看不到其他手牌、私密候选、身份、token、未公开拼点或牌堆顺序。
8. 开局和每类操作后的卡牌守恒、原子提交、rev 与去重行为仍通过。所有“本机验证”和“跨互联网验证”分别记录。

计划完成后先实施第一批，再根据实际操作反馈调整后续顺序。本文件保留原规划；当前本地实现、验证范围与限制以 UX_IMPLEMENTATION.md 为准，尚未据此发布线上站点。
